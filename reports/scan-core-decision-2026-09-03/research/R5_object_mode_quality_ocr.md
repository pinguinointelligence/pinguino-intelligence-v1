# R5 — Object-Mode Live Scan Core: Localization, Tracking, Frame Quality, Label-Text Evidence

**Scope**: evidence file for an architecture decision on the LIVE SCAN CORE of a mobile-web PWA (iPhone Safari + Android Chrome) that must handle barcode-less physical objects (banana, apple, milk carton, Oreo box, can, bottle) plus label text — localize, track, judge frame quality, guide the user, and accumulate evidence, entirely **before** any expensive semantic identification. Research date: 2026-09-03.

**Methodology note on rigor**: Every numeric claim below was checked against a directly-fetched page where possible. In several cases the search tool's own synthesized summary stated a specific number that could **not** be confirmed when the same URL was fetched directly (e.g. a claimed "iPhone X, 2–20s per image" Tesseract.js figure, a claimed "171ms YOLO11n" figure, and a claimed "4.70M" PP-OCRv4 detector size). Those unconfirmed numbers are explicitly flagged or dropped rather than repeated as fact. `[VERIFIED source](URL)` below means the cited number/quote was read directly from that URL's fetched content this session. `[CLAIM]` means it came from a search-engine synthesis I could not independently re-confirm by direct fetch, or is well-known but not re-verified this session. `[INFERENCE]` is my own reasoning connecting verified facts.

### 1.3 Class-agnostic / salient localization ("the thing the user is holding up")

Because COCO has no generic box/carton/package class, and no small in-browser model handles open-set "any product" detection out of the box, the practical options are:

- **Saliency models — U2-Net / U2-Netp**: the full U2-Net is 176.3 MB; the lightweight **U2-Netp ("portable")** variant is **4.7 MB** on disk. [VERIFIED source](https://github.com/xuebinqin/U-2-Net) License: Apache-2.0. [VERIFIED source](https://github.com/xuebinqin/U-2-Net) A community ONNX port describes U2netp as loading "instantly" and running at roughly **30 ms/image on CPU**, adequate for the large majority of background-removal/saliency use cases. [CLAIM — this specific latency figure came from a search-engine synthesis referencing a Hugging Face model card, not independently re-fetched this session]. **[INFERENCE]**: at 4.7 MB and ~30 ms CPU (unverified but plausible given the model's small size), U2-Netp is a realistic "where roughly is the salient thing in frame" signal usable as a fallback/complement to COCO detection for box-shaped objects the detector can't name.
- **Objectness / center-prior heuristics**: classical (pre-CNN) saliency literature establishes that camera photos strongly bias the photographed subject toward the frame center (a "center-prior," often modeled as a Gaussian bias), and that objectness scoring (edge density, contrast, background-difference) can rank candidate regions without any semantic classifier. [CLAIM — general literature synthesis, e.g. the "distribution of salient objects in web images" line of research] **[INFERENCE]**: for a hand-held scanning UX specifically (as opposed to arbitrary photos), the center-prior is an even stronger, nearly-free heuristic — the object being scanned is almost always deliberately centered by the user — and combining it with simple contrast/edge-density objectness scoring is a viable zero-model fallback when neither COCO nor a saliency net fires confidently.
- **Background subtraction**: viable only when the scanning surface is controlled (e.g., a fixed mat/table) and not viable for a general hand-held "point at anything" flow; not further supported by sources found in this pass. [INFERENCE — not independently researched further given low relevance to a general PWA scanner]
- **MediaPipe Interactive Segmenter (Web)**: takes a point-in-image plus estimates the boundary of the object at that point, returning a segmentation mask; ships as part of `@mediapipe/tasks-vision`, supports CPU/GPU delegate selection, and the docs recommend the newer stateful `InteractiveSegmenter` API (`setImage()` once, then repeated interactive calls) over the deprecated `InteractiveSegmenterLegacy`, explicitly for "significantly improved interactive performance." [VERIFIED source](https://developers.google.com/edge/mediapipe/solutions/vision/interactive_segmenter/web_js) No latency numbers or model size are published on the fetched page. [gap — not found] **[INFERENCE]**: Interactive Segmenter requires a user-supplied point/click, which does not map cleanly onto a fully-automatic live scan loop — it is better suited as an assist tool (e.g., "tap the object") than as the primary automatic localizer, whereas the plain **Image Segmenter** (category/foreground mask, no point needed) is the more relevant automatic-mode building block, though this report did not find specific web latency numbers for it either. [gap]

- **Google Lens**: the live-view UX overlays a camera viewfinder with per-object visual indicators as the user pans; each indicator is interactive (tapping it issues the actual content/search request), and indicators appear/disappear/move as objects enter, leave, or shift within frame. [CLAIM — synthesized from a Google patent filing on "real time object detection and tracking" plus general product description] Google's own marketing states Lens "instantly scans the image to detect objects, text, places, products, animals ... and within seconds ... displays relevant search results." ## 2. Tracking in the browser

- **Does the Web Tasks-Vision Object Detector have a tracker? No, not as a documented feature.** The JS API surface fetched directly exposes only `detect()`/`detectForVideo()`, `scoreThreshold`, `maxResults`, and category allow/deny-lists — no track-ID or persistence option. [VERIFIED source](https://developers.google.com/edge/mediapipe/solutions/vision/object_detector/web_js) MediaPipe *does* have a sophisticated detector+tracker fusion — but it lives in the older, C++/mobile-graph **"Box Tracking" legacy solution**, explicitly marked in its own docs as forwarding to "MediaPipe Legacy Solutions." [VERIFIED source](https://github.com/google/mediapipe/blob/master/docs/solutions/box_tracking.md) **[INFERENCE]**: this legacy graph is not exposed through the modern `@mediapipe/tasks-vision` npm package used on the web; a web app must roll its own cross-frame association (e.g., a small IoU/SORT layer, §2.2) on top of the stateless per-frame `detectForVideo()` calls.
- The legacy Box Tracking architecture is nonetheless the best-documented reference for **how the detector+tracker split should work**, and is directly relevant even if reimplemented by hand in JS:
  - A `PacketResampler` calculator **subsamples incoming video frames to 0.5 fps** before they reach the (expensive) object-detection subgraph — i.e., roughly one detector run every two seconds — and this rate is explicitly stated to be configurable. [VERIFIED source](https://github.com/google/mediapipe/blob/master/docs/solutions/box_tracking.md), corroborated at [VERIFIED source](https://developers.googleblog.com/object-detection-and-tracking-using-mediapipe/)
  - The tracking subgraph runs **"in real-time on every incoming frame,"** i.e., at full camera frame rate, independent of the throttled detector. [VERIFIED source](https://github.com/google/mediapipe/blob/master/docs/solutions/box_tracking.md)
  - Association between new detections and existing tracks uses **IoU** to "remove obsolete or duplicated boxes," while between detections the tracker follows **motion vectors extracted from image features** (not full optical flow at the pixel level) to keep boxes "temporally consistent," explicitly citing reduced jitter as the payoff. [VERIFIED source](https://developers.googleblog.com/object-detection-and-tracking-using-mediapipe/)
  - **[INFERENCE]**: this 0.5 fps-detector / full-fps-tracker split is the direct architectural answer to the prompt's question about how commercial scanners "keep a highlight glued to a moving target between detector runs" — run the expensive semantic/localization model rarely, run a cheap geometric tracker every frame, and reconcile with IoU whenever a fresh detection lands. The same pattern generalizes directly to a hand-rolled browser implementation using `detectForVideo()` every N frames plus SORT-style tracking on the frames in between.
- **Lightweight IoU + Kalman (SORT)**: SORT combines a constant-velocity **Kalman filter** per track (predicting the next box from motion history) with the **Hungarian algorithm** solving track↔detection assignment from a pairwise-**IoU** cost matrix; it uses bounding-box geometry only (no appearance features), which is exactly why it is fast — "scales to hundreds of frames per second on typical hardware." Its known weakness is identity switches/fragmentation under long occlusion or heavy crowding, which is a minor concern for a single-object "point the camera at the thing you're scanning" use case. [CLAIM — general SORT literature synthesis, e.g. Roboflow's SORT documentation] **[INFERENCE]**: SORT's per-frame cost (a handful of 4×4 Kalman matrix updates plus an IoU matrix for at most a few boxes) is trivially cheap in JS — this is squarely realistic for a mobile browser main/worker thread, unlike running a neural net every frame.
- **Lucas–Kanade optical flow**: ships in **standard OpenCV.js** — official OpenCV documentation includes a dedicated browser tutorial page (`js_optical_flow_lucas_kanade.html`) built around `cv.calcOpticalFlowPyrLK()`, with a pyramidal (multi-level, default `maxLevel=3`) implementation and a configurable window size (default 21×21) trading tracking precision for compute cost and robustness to larger displacements. [VERIFIED source](https://docs.opencv.org/3.4.20/db/d7f/tutorial_js_lucas_kanade.html) No official browser-specific fps/latency numbers were found for this in the fetched docs. [gap]
- **KCF / MOSSE / CSRT in OpenCV.js — NOT available in standard prebuilt distributions.** This is an important, concrete negative finding: multiple OpenCV GitHub issues and forum threads confirm "there is no Tracking module for OpenCV.js in the standard distribution" — the classical single-object trackers (KCF, MOSSE, CSRT, plus BOOSTING/MIL/TLD/MEDIANFLOW/GOTURN) exist in OpenCV's C++ `tracking` (contrib) module, but the default precompiled `opencv.js` build does **not** expose them. Getting them requires a **custom Emscripten build** with `-DBUILD_opencv_tracking=ON` plus manual entries added to `opencv_js.config.py`. [VERIFIED source](https://github.com/opencv/opencv/issues/15607), corroborated at [VERIFIED source](https://answers.opencv.org/question/218980/how-to-load-any-of-this-tracking-algorithm-in-opencvjsboosting-mil-kcf-tld-medianflow-goturn-mosse-or-csrt/) **[INFERENCE]**: this rules out "just call `cv.TrackerKCF.create()`" as a drop-in browser option unless the team is willing to ship a custom OpenCV.js build (larger download, own maintenance burden) — for most teams, hand-rolled SORT (IoU+Kalman, pure JS, no OpenCV needed) or OpenCV.js's standard, already-shipped Lucas-Kanade optical flow are the pragmatically available choices, not the classical single-object trackers.
- **Cost per frame, qualitatively ranked cheapest→priciest** [INFERENCE, synthesizing the above]: IoU/Kalman bookkeeping (near-zero) < sparse Lucas-Kanade on a handful of corner points < dense/many-point optical flow < any neural detector inference (tens to hundreds of ms per §1.2). A practical live loop should run the detector at a low duty cycle (MediaPipe's own reference point is 0.5 fps, though a scanning UX can likely afford higher, e.g. 2–5 fps, given it targets a single foreground object rather than a general scene) and interpolate every other frame with IoU/Kalman and/or sparse optical flow to keep the on-screen highlight visually glued to the object at full camera frame rate (typically ~30 fps via `getUserMedia`).

## 3. Frame quality assessment for scanning

- **Blur — variance of Laplacian**: `cv2.Laplacian(gray, cv2.CV_64F).var()`; low variance ⇒ blurry, on the reasoning that a sharp image has a wide spread of both edge-like and non-edge responses. The most commonly cited **default threshold is 100.0**, but the source is explicit that this must be tuned per dataset: too low a threshold marks sharp images as blurry, too high lets real blur through, and the right value is "quite subjective to the contents of the image(s)." [VERIFIED source](https://pyimagesearch.com/2015/09/07/blur-detection-with-opencv/) A broader threshold range of roughly **100–1000** appears across various implementations depending on domain. [CLAIM — general synthesis]
- **Tenengrad**: a Sobel-gradient-energy-based focus measure (a.k.a. "Sobel Energy"); squares and sums horizontal+vertical Sobel gradients per pixel, is described as rotation-invariant/isotropic, and multiple sources report it and Laplacian-variance as the two most reliable, "consistently identif[ying] the sharpest frame" among compared methods, with a Tenengrad + hill-climbing search reported best for fast-moving small targets (UAV autofocus context). [CLAIM — search synthesis of multiple academic/practitioner sources; a direct fetch of the OpenCV.org comparative-study blog post specifically was blocked with an HTTP 403, so that primary source could not be independently confirmed this session]
- **FFT / high-frequency-energy blur detection**: measures the proportion of high-frequency spectral energy after a 2D FFT; a sharp image retains more high-frequency content than a blurred one. [CLAIM — general, well-established technique; not independently re-verified against a specific primary source this session]
- **CPBD (Cumulative Probability of Blur Detection)**: a perceptual no-reference sharpness metric from Arizona State University's Image/Video/Usability lab, built on a probabilistic model of human "just-noticeable-blur" perception at detected edges, pooled into a single cumulative-probability score; higher = sharper, and it is specifically designed to rank *relative* blurriness across varied image content (not just binary sharp/blur), unlike simpler no-reference metrics. A maintained Python port (`python-cpbd`) exists. [CLAIM — synthesized from the IEEE paper abstract and the GitHub port's own description, not independently fetched] **[INFERENCE]**: CPBD is more principled than Laplacian variance but also more computationally involved (edge detection + per-edge probability modeling); for a live 30 fps loop, Laplacian variance / Tenengrad remain the pragmatic choice, with CPBD reserved (if used at all) for scoring the small shortlist of "best frame" candidates rather than every frame.
- **Motion blur via inter-frame displacement / IMU**: not covered by a dedicated source found in this pass beyond the general observation that optical-flow displacement magnitude (§2) or the device's accelerometer/gyroscope (accessible in a PWA via the Generic Sensor API / `devicemotion`, subject to iOS Safari's stricter permission gating) can serve as a cheap proxy for "the camera is moving too fast right now, don't bother scoring this frame for sharpness." [INFERENCE — architectural reasoning, not a dedicated citation]
- **Glare / specular highlight detection**: standard approach thresholds in **HSV** — high Value combined with low-to-moderate Saturation (a "blown," desaturated-white highlight) flags a specular region; more advanced versions use a 2D luminance×saturation histogram, or adaptive saturation thresholds tuned to overall brightness (one endoscopic-imaging paper cites adaptive thresholds of **τ ≈ 0.3 / 0.8 / 1.1** for high/medium/enhanced-low brightness conditions respectively). [CLAIM — synthesized from endoscopic-image specular-highlight papers; note the *domain* is medical endoscopy, not consumer product photography, so the exact threshold constants are illustrative rather than directly transferable] **[INFERENCE]**: the underlying mechanism (flag saturation-collapsed, near-maximum-value pixel clusters as glare) generalizes fine to grocery packaging (glossy labels, foil, plastic wrap) even though the specific τ constants would need re-tuning for that domain.
- **Exposure via histogram**: classic technique — a histogram with mass piled at the left edge indicates clipped/underexposed shadows, mass at the right edge indicates clipped/overexposed highlights; some implementations use a centroid-luminance check against a threshold, others a "clipped-pixel score" + "tonal-distribution score" composite. [CLAIM — general technique, patent-literature and photography-reference synthesis, not a single peer-reviewed primary source]
- **Too close / too far**: inferred directly from detector bounding-box area relative to total frame area — no dedicated source needed beyond the geometric definition. [INFERENCE]
- **Cut off**: bounding box touching or clipped by a frame edge. [INFERENCE — simple geometric check]
- **Angle / perspective**: the document-scanner literature (jscanify, jscanify-style OpenCV.js pipelines, Scanbot/Dynamsoft blog write-ups) establishes the standard pipeline — grayscale → blur → Canny edge detection → contour extraction → find the largest 4-point contour ("quad") → `cv.warpPerspective()` using the quad's corner homography to rectify. The degree of deviation of the detected quad from a "square-on" rectangle (e.g., unequal opposite-side lengths, corner angles far from 90°) is a direct, cheap proxy for capture angle/perspective distortion. [VERIFIED source](https://github.com/opencv/opencv/blob/master/doc/js_tutorials/js_assets/js_optical_flow_lucas_kanade.html) *(Lucas-Kanade tutorial confirms OpenCV.js availability generally)*; document-scanner pipeline steps themselves [CLAIM — synthesized from Dynamsoft/Scanbot/jscanify write-ups, not independently re-fetched with full content this session].
- **Contrast**: standard global-histogram spread (e.g., standard deviation of pixel intensities) — not independently sourced beyond general knowledge in this pass. [INFERENCE]
- **Tiny no-reference IQA (BRISQUE-class) models**: BRISQUE itself scores "naturalness" via locally-normalized-luminance scene statistics feeding a trained regressor (lower = better quality), and is the reference baseline the field compares against. [CLAIM — general/MATLAB-doc synthesis] A recent lightweight variant (**GSBIQA**, saliency-guided) is reported to run at **52 images/second on CPU only**, explicitly framed by its authors as suited to "mobile and edge devices." [CLAIM — from an arXiv paper abstract synthesis, not independently fetched in full] **[INFERENCE — the key architectural conclusion for this section]**: no evidence was found of any BRISQUE-class no-reference IQA model actually shipped as a browser-ready (ONNX/TFJS/WASM) artifact with a published in-browser latency; realistically, running a *second* neural network purely for quality scoring is unnecessary overhead here — the classical, essentially free signals above (Laplacian-variance/Tenengrad for blur, histogram clipping for exposure, HSV thresholding for glare, bbox geometry for framing/cutoff, quad-fit for angle) already cover every quality dimension the prompt asks about, at a tiny fraction of the compute cost of any learned IQA model, and are the ones this report recommends.

- **Tesseract.js on phones**: qualitative, well-documented complaint pattern (an open, unresolved GitHub issue asks specifically "how to increase the speed of OCR using tesseract.js in mobile app" because "OCR ... is taking a long time"), but **no specific, verifiable seconds-per-image number could be confirmed by direct fetch** of that issue thread. [VERIFIED source (issue exists, complaint is real, no numbers given)](https://github.com/naptha/tesseract.js/issues/611) *(An earlier search-engine synthesis claimed a specific "iPhone X, 640×640, 2–20+ seconds" figure attributed to this same issue; the issue's actual fetched content contains no such number, so that figure is not reported as fact here.)* The library's own performance guide confirms multi-second-class overhead is plausible: **setup (`createWorker`) frequently dominates total runtime**, not recognition itself, so the top recommendation is to create the worker once and reuse it rather than per-image; a second recommendation is to opt into "fast"-optimized language data (`tessdata.../4.0.0_fast`) instead of the accuracy-optimized default; default language data is **~2 MB**, worst case (Legacy engine + Chinese-Simplified) **~20 MB** to download. [VERIFIED source](https://github.com/naptha/tesseract.js/blob/master/docs/performance.md)
- **A faster alternative exists**: `tesseract-wasm` (a from-scratch Emscripten/WASM port by robertknight, not affiliated with Tesseract.js) needs only a **~2.1 MB** download (with Brotli compression) for the engine plus English training data, and uses **WebAssembly SIMD** where available (Chrome ≥91, Firefox ≥90, Safari ≥16.4) specifically to accelerate the matrix-multiply-heavy recognition path. [VERIFIED source](https://github.com/robertknight/tesseract-wasm) A one-off developer benchmark (not the project's own published number, found via a linked social-media post, so treated as anecdotal) claimed a ~10× speedup over Tesseract.js on **large documents** (60 s → 6 s for a 150 DPI A4 scan) — this is a full-page-of-text workload, not a small live-camera product-label crop, so it does not directly transfer, but it is directionally consistent with SIMD + modern-toolchain builds mattering a great deal. [CLAIM]
- **PaddleOCR PP-OCRv4 (mobile) — via ONNX Runtime Web**: PaddleOCR's own docs confirm PP-OCRv4 ships a dedicated mobile-optimized detector for edge deployment, and that ONNX Runtime is a supported inference backend (as an alternative to native Paddle Inference). [VERIFIED source](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/OCR.en.md) The **RapidOCR** project packages PP-OCR models specifically for ONNX Runtime (also OpenVINO/MNN/TensorRT/PyTorch), under **Apache-2.0** for its own engineering code, while explicitly noting **the OCR model weights' copyright is retained by Baidu** — i.e., the permissive Apache-2.0 grant covers the surrounding tooling, and the pretrained-weight redistribution terms are a separate question worth a legal check. [VERIFIED source](https://github.com/RapidAI/RapidOCR) Concrete model-size numbers, directly fetched from Hugging Face model cards:
  - **PP-OCRv4_mobile_rec**: model size **"11 M"** (~11 MB), reported recognition accuracy **83.28%**. [VERIFIED source](https://huggingface.co/PaddlePaddle/PP-OCRv4_mobile_rec)
  - **PP-OCRv4_mobile_det**: the model card fetched directly did **not** state a size figure (only per-scenario accuracy numbers, e.g. printed Chinese 0.872, handwritten English 0.369, averaging 0.624 across 13 categories). [VERIFIED source](https://huggingface.co/PaddlePaddle/PP-OCRv4_mobile_det) *(A separate search-engine synthesis claimed "4.70M" for this same model, but that number is unconfirmed against the directly-fetched card and is not reported as fact.)*
  - No in-browser (ONNX Runtime Web / WASM / WebGPU) latency numbers were found for PP-OCRv4 mobile models in this pass. [gap]
- **Apple Live Text (`VNRecognizeTextRequest`) / ML Kit Text Recognition v2 — native-only reference points, not directly usable in a PWA**: both are on-device, no-network-call OCR APIs, but they are native SDK surfaces (Vision framework on iOS, ML Kit on Android) with **no path for a Safari/Chrome web page to call them directly** — a PWA cannot invoke `VNRecognizeTextRequest` or ML Kit's `TextRecognizer`. [INFERENCE — standard, well-established platform-API fact] Both APIs expose a fast/lower-accuracy vs. slower/higher-accuracy mode trade-off (`VNRequestTextRecognitionLevel .fast` vs `.accurate`; ML Kit's guidance to downsize images and to throttle/drop frames via `ImageAnalysis.STRATEGY_KEEP_ONLY_LATEST` on Android). [CLAIM — search synthesis of Apple/Google's own docs] **[INFERENCE]**: these exist in this report purely as *reference points* for what "OCR done right" looks like at the native-platform level (near-instant, frame-throttled, degrade-gracefully) — a browser-based OCR stack should copy the *pattern* (downscale first, throttle to available frames, offer a fast/degraded mode) even though it cannot call the native API itself.
- **Text DETECTION only, as a cheap "there is a label here" signal**: DBNet ("DB") is described as a representative real-time text detector; commonly paired with lightweight backbones (**MobileNetV1/V2/V3, ShuffleNetV2**) specifically to hit real-time/mobile budgets, and DBNet++ (ResNet-50 variant) is reported to beat EAST by 7.2% accuracy while running twice as fast — though that specific comparison uses a ResNet-50 backbone, not the lightweight mobile ones relevant here. [CLAIM — search synthesis of DBNet/PP-OCR literature] CRAFT is a **character-level** detector, reported to localize difficult/irregular-font words better than EAST because it works character-by-character rather than at the word/line level. [CLAIM] **[INFERENCE]**: a lightweight DB-style detector (mobile backbone) is the right shape for a live-loop "does this frame contain readable label text, and roughly where" signal — much cheaper than running full recognition, and directly reusable as a trigger for §6's capture strategy.
- **Multi-frame text accumulation / voting**: the general, well-established pattern is to associate each frame's OCR output with a tracked region (via §2's tracker) and merge repeated reads with a **confidence-weighted or majority vote**, which suppresses transient single-frame misreads (motion blur, glare flicker, momentary occlusion) without needing any one frame to be perfect. [INFERENCE — this is a standard, widely-used pattern in video-OCR systems; no single primary paper is cited here because the specific named "techniques" surfaced by search summarization for this sub-topic could not be independently confirmed and are deliberately not repeated as attributed findings]
- **Conclusion on live-loop OCR feasibility** [INFERENCE, synthesizing the above]: **full OCR recognition (Tesseract.js-class, and very likely PP-OCRv4-mobile-class too) is not realistic to run on every frame of a live 30 fps camera loop** on typical phone browsers — the dominant reported failure mode is multi-second-class latency and mandatory UI-thread offload (Web Worker), which by itself rules out a naive per-frame call. The right architecture is a **two-tier split**: (1) a cheap, small text-*detection*-only model (or even simpler, edge-density/contrast heuristics tuned for text-like texture) running periodically in the live loop purely to answer "is there a label here, and where" and to help drive the capture-quality gate in §6; (2) full OCR *recognition* (Tesseract.js/tesseract-wasm/PP-OCRv4-mobile, whichever wins a follow-up bake-off) run **once, triggered, on the single best accumulated frame** — not in the live loop. This matches how the native reference points (Live Text, ML Kit) behave in practice (frame-throttled, not brute-force every-frame) even though a PWA can't call those APIs directly.

This requires either (a) an on-device embedding model (MobileCLIP-class if a native-app wrapper or future faster WebGPU stack makes the latency work; SigLIP-class today, given it's the one with an actual browser-ready export) matched via retrieval against a product catalog, (b) OCR-extracted brand/text (§4) matched against a catalog, or (c) a remote VLM/cloud call — run once, on the best frame(s) this Scan Core hands off, exactly mirroring how Apple's own Visual Look Up escalates only its hardest case (landmarks) to a server-side embedding match while keeping everything else on-device (§1.4).

## 6. Best-frame / multi-view capture strategies

- **Vivino** (wine labels): **single-photo**, forgiving-capture UX — "point your phone at the wine label, you don't need to frame it perfectly or hold especially still," matched within "a second or two." Explicit user guidance prioritizes **lighting over steadiness** ("a brightly lit label in natural light scans faster and more reliably than a dimly lit one, even with a perfectly still hand"), plus "get close enough that the label fills most of the frame" and "keep your phone perpendicular to the bottle to reduce distortion." On a failed match, the app offers **manual text search** or **submits the label for human review**, typically resolved "within a few hours." Backed by Vuforia computer-vision tech. [VERIFIED source](https://www.vivino.com/en/wine-news/how-the-vivino-label-scanner-works)
- **Amazon Lens Live** (2026 feature): described in Amazon's own release messaging as "an accurate, lightweight computer vision object detection model running **on-device**" that identifies products live as the camera pans, **without requiring the user to snap a photo** — matches surface continuously as a swipeable results carousel at the bottom of the live camera view. [CLAIM — from Amazon's own official blog post via search synthesis, not independently re-fetched in full this session] **[INFERENCE]**: this is architecturally the closest existing production analogue to the Scan Core described in this prompt — on-device detection driving a continuous live result stream rather than a discrete capture-then-upload step.
- **Yuka**: primarily **barcode-first**, but maintains a distinct, explicitly documented **fallback path for barcode-less products** (a dedicated help-center article, "The product I want to scan doesn't have a bar code. What should I do?"), and separately treats product **photos as optional/toggleable** ("Include photos" setting) due to on-device storage concerns in its offline mode — i.e., photo capture is decoupled from the core identification flow rather than mandatory. [CLAIM — synthesized from Yuka's own help-center pages via search, not independently fetched in full]
- **Open Food Facts**: explicitly supports adding a product that has no barcode; photography guidance recommends a **plain/white background**, **vertical orientation**, minimal shadows/reflections, and photos taken "in a specific order" — implying a defined multi-shot sequence (commonly front-of-pack, ingredients list, nutrition table in OFF's actual product-contribution flow) rather than a single capture. [CLAIM — synthesized from OFF forum/help sources via search, not one authoritative page independently fetched in full] **[INFERENCE]**: OFF's ordered-multi-photo convention is the clearest real-world precedent for "front label first, second view only if needed" evidence accumulation named in the prompt.
- **Burst + select-sharpest**: a well-established general mobile-photography pattern — iOS visually flags a recommended frame within a burst/Live Photo sequence, and the underlying technique (evaluated in academic/computational-photography contexts too) is a **gradient-based sharpness metric** scored per candidate frame, keeping the maximum. [CLAIM — general synthesis, one computational-photography paper specifically describes scoring a gradient-based sharpness metric on the green channel of raw burst frames to pick a reference frame] **[INFERENCE]**: this generalizes directly into a live-loop policy — rather than a single user-triggered "capture" button, continuously score every incoming frame (bbox present + stable, Laplacian-variance/Tenengrad above threshold, no glare/exposure clipping, not cut off, low perspective skew) and simply retain the highest-scoring frame seen so far per "view," replacing it whenever a better one arrives.
- **"Enough evidence" completion criteria**: none of Google/Apple/Amazon/Vivino/Yuka publish their internal thresholds for when a live-view result is considered final. The consistent *pattern* across every one of these consumer products, however, is a **soft, forgiving trigger with a cheap manual escape hatch** — imperfect framing/stability is explicitly tolerated (Vivino says so outright), recognition windows are short (Vivino: "a second or two"; Google Lens: "within seconds"), and every product provides a fallback when automatic matching fails (manual text search, human review queue, or simply "product not found, try again"). None of them appear to enforce a hard, blocking, client-side multi-angle checklist before allowing a result. [INFERENCE — synthesized pattern across all fetched/searched sources above]
- **[INFERENCE] — a synthesized, defensible capture-completion strategy for this Scan Core**, combining OFF's ordered-multi-photo convention with the burst/select-sharpest pattern and this report's own quality/OCR findings: accumulate the best-scoring frame continuously (per §3's quality gate) while a stable bounding box is present; treat "front-of-pack evidence" as sufficient once a best-frame simultaneously clears the quality bar **and** the cheap text-detection signal (§4) confirms a label/text region is visible and legible-looking; escalate to requesting a **second view** only when evidence remains insufficient after some stability window (e.g., no legible text region found on any frame, or the coarse classifier from §5 is not confident) — mirroring OFF's "front label, then more views if needed" pattern — rather than always demanding a fixed number of angles up front.

## Synthesis: recommended Scan Core shape

[INFERENCE — this section is this report's own synthesis, not a quoted source]

- **Localization**: MediaPipe Tasks-Vision `ObjectDetector` (EfficientDet-Lite0, Apache-2.0, already ships as WASM+WebGL web SDK) as the primary "named COCO thing" path (banana/apple/orange/bottle/cup/bowl), *plus* a class-agnostic fallback (U2-Netp saliency, 4.7 MB, Apache-2.0, or a center-prior/objectness heuristic) to catch the box/carton/can/package majority that COCO structurally cannot name. Avoid Ultralytics YOLOv8n/YOLO11n unless the Enterprise license is purchased — AGPL-3.0's SaaS-reaching copyleft is a real, confirmed blocker for a closed-source commercial PWA; YOLOX/NanoDet/PP-PicoDet (all confirmed Apache-2.0) are the license-clean fallbacks if a YOLO-style anchor-free detector is specifically wanted.
- **Tracking**: no ready-made web tracker ships with MediaPipe's modern Tasks Vision API — hand-roll a small IoU+Kalman (SORT-style) association layer in plain JS (cheap, no OpenCV needed), run the neural detector at a low duty cycle (MediaPipe's own reference point is 0.5 fps; a scanning UX can likely push higher), and interpolate every other frame so the on-screen highlight stays glued to the object at full camera fps. Do not plan around OpenCV.js's classical trackers (KCF/MOSSE/CSRT) — they are absent from standard prebuilt opencv.js and require a custom Emscripten compile.
- **Quality gate**: entirely classical, near-zero-cost signals — Laplacian-variance/Tenengrad for blur, histogram-clipping for exposure, HSV saturation/value thresholding for glare, bbox-vs-frame-area for too-close/-far, bbox-edge-touching for cut-off, quad-fit deviation for angle/perspective. No learned no-reference IQA model is justified; none was even found shipped browser-ready.
- **OCR**: not in the live 30 fps loop. A lightweight text-*detection*-only signal (small DB-style/mobile-backbone model, or even a cheap edge-density heuristic) can run periodically in the loop to flag "a label is visible here" and help drive capture completion; full recognition (Tesseract.js, tesseract-wasm, or PP-OCRv4-mobile via ONNX Runtime Web — a follow-up bake-off should pick among these) runs once, off the main thread, triggered on the single best accumulated frame.
- **Semantic boundary**: the Scan Core's own on-device budget stops at coarse categorization (a small ImageNet-class or custom-trained MobileNetV3-Small-class model — produce type, rough packaging shape). Brand/SKU-level identification is explicitly downstream: an embedding-based retrieval step (SigLIP-class is the one verified to already have a browser-ready ONNX/Transformers.js export today; MobileCLIP is faster but its published numbers are native-CoreML, not browser, and its weights carry Apple's research-only terms of use) or a cloud VLM call, run once per accumulated best-frame — the same on-device/escalate-when-needed pattern Apple's own Visual Look Up uses in production.
