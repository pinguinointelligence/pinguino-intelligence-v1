## Answers
1. **≥ 15 processed fps at 1280? NO — 7.1 fps.** Halving the pixel count bought +31 %.
2. **Total budget ≤ 60 %? NO — 83 %.** Main-thread capture fell only from 63 to 50 ms per frame: the `drawImage` + `getImageData` readback has a large fixed cost independent of the target size.
3. **Locate + ROI ≤ 40 ms p95? YES — 20.3 ms** (was already passing at 2 MP: 22.7 ms).
4. **Reliability materially degraded? Yes beyond 25 cm.** 30 cm and the 40 cm approach went from confirmed to zero reads (modules ≈ 1.4 px at 720 wide); 12–25 cm, small EAN-8, can, glare, motion, low light unchanged or faster.
5. **Solvable mainly by resolution/workload control? NO.** The per-frame cycle is sequential capture (50 ms, main thread, mostly fixed) → worker (35–50 ms) → next rVFC tick, which caps this device near 7–10 fps whatever the plane size, and any further downscale sacrifices the far codes. Android needs a structural change of the acquisition path, not a smaller plane.

## Recommended Phase 1 direction (final)
1. **Move frame acquisition off the main thread and pipeline it.** Transfer `VideoFrame` (Chrome) / `ImageBitmap` (fallback) to the worker; read pixels there via OffscreenCanvas while the main thread only schedules; capture frame N+1 while frame N decodes. The harness already implements both paths behind the „Ścieżka przekazania klatki” selector (B9, unmeasured on phones) — the first Phase 1 spike is a 60 s loop on the Note10+ with each path, no other change.
2. **ROI-first decoding at native resolution.** Keep the full-resolution frame in the worker; run saliency on the 320-px pyramid, decode the candidate crop at native pixels every frame (≤ 2 ms measured), and run a full-frame pass only when no candidate exists or every N-th frame. This restores 30–40 cm reads without paying 2 MP full-frame decodes.
3. **Cheaper saliency:** integer block sums on a 240-px plane (13–17 ms today → target ≤ 5 ms), then the worker budget per frame is ≈ 10 ms.
4. **Confirmation rules from the corpus:** agreement across different frames only; rectified-crop reads never confirm alone (D3 can alias); gate the fast lane on module width / lineCount or require three frames for small candidates (D1 40 cm aliases); one product = one confirmed value per scene window.
5. **Camera policy:** Android → ranked primary sensor (never `facingMode` alone); iOS → virtual multi-lens camera (macro auto-switch) — both now in the harness.
6. **Thermal budget:** design for the throttled regime (×2 after ~5 min on the Note10+); target ≤ 50 % worker duty cold so 15 fps survives the step.
Expected Android outcome with 1–3: worker ≈ 10–15 ms/frame, acquisition overlapped → 15 fps sustained plausible even throttled; to be measured, not assumed.
